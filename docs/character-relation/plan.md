# 登場人物関係（Character Relation）

## 概要

登場人物同士の関係（`character_relation_transaction`）の重複ルールと、画面上の置き場所・操作を決める。関係の API は一覧・登録・更新・削除を実装済みで、関係を含む人物詳細の取得 API も実装済み（U13）。マイグレーションを適用していないため、いずれも実 DB では未検証（U3）。

作品詳細のタブ構成は `docs/work-detail-screen/plan.md` を参照。

## 前提（スキーマ）

- 関係は「人物 → 相手 + 関係（文字列）」の向きを持つ（`character_id`・`target_character_id`・`relation_name`）
- 関係名の列は `relation_name`（2026-11-01 に `relation` から変更。テーブルの1行自体が「関係」のため、`relation` では行全体か関係名の文字列かが区別できない。ドメインの値オブジェクトは `CharacterRelationName`。既存の値オブジェクトと同じ「Entity 名 + 項目名」の命名）
- 複合 FK により、同じ作品の人物同士でのみ作成できる。自分自身との関係は CHECK 制約で禁止
- 関係は自由入力の文字列（マスタにしない）

## 決定事項

### ユーザー決定事項

- U1: 同じ2人の間で同じ関係（trim 後に完全一致）は、向きを問わず重複として禁止する（2026-11-01）
  - 例: 「A → B：兄」がある状態で、「A → B：兄」「B → A：兄」はどちらも登録できない。「B → A：弟」は登録できる
  - DB: 部分一意インデックス `character_relation_transaction_pair_relation_name_unique` を `schema.ts` に追加済み（`min(character_id, target_character_id)`・`max(character_id, target_character_id)`・`relation_name`。`delete_flg = 0` の行が対象）
  - ドメインでも判定する（登録・更新時に、(人物, 相手, 関係) または (相手, 人物, 関係) に一致する未削除の行があれば err。更新では自身の行を除外する）。画面からもまったく同じ関係は登録できないようにする
  - 2026-11-07 に変更済み: `docs/delete-restore/plan.md` の U11 により、削除済みの関係も含めて判定し、一意インデックスの `delete_flg = 0` の条件を外した（マイグレーションは未作成）。判定はドメインサービスの `validate`（Result）で行う。削除されていない関係と重複した場合は `DUPLICATE_RELATION`、削除済みの関係とだけ重複した場合は `DUPLICATE_DELETED_RELATION`（409「削除済みの人物関係に同じ関係があります。復元するか、別の関係にしてください。」。文言は Claude の提案をユーザーが承認）
    - 関係の復元 API・操作場所は未定のため、現時点では文言の「復元」を行う手段がない
- U2: 関係は、関係する両方の人物の画面に表示する
- U3: マイグレーションは今回は生成・適用しない
- U4: 関係名の上限は 50 文字（`CharacterRelationName.RELATION_NAME_MAX_LENGTH`。文の形で表示する短いラベルのため。職業と同じ上限）
- U5: 自分自身との関係（人物と相手が同じ）は、`CharacterRelationEntity` の `create`・`update` で err `CHARACTER_RELATION_SELF` を返す（画面で同じ人物を選ぶのは外部入力が原因のため）。`reconstruct` は DB の CHECK 制約で除外済みのため throw する
- U6: 編集では人物・相手・関係名のすべてを変えられる（`CharacterRelationEntity.update`。当初は関係名だけにする案だったが、人物を間違えたときに削除して入れ直す必要がなく、追加と同じダイアログを使えるため変更）
  - 更新の Usecase では、変更後の人物・相手がその関係と同じ作品の削除されていない人物かを確認する（登録と同じ確認）
  - 重複（U1）は変更後の (人物, 相手, 関係名) で判定し、自身の行を除外する
- U7: 関係の一覧では、人物または相手が論理削除されている関係を除外する（2026-11-02）
  - 当初の理由（Claude からの提案）は、関係の行を変更しない（`docs/delete-restore/plan.md` P2）ため、人物を復元すると関係も一覧に戻ること。U12 により、削除済みの人物には関係が残らない想定になったため、この理由は当てはまらなくなった
- U8: 人物・相手が同じ作品の削除されていない人物かの確認は、作成用の Repository に追加せず、ドメインサービス（`CharacterValidityDomainService`）に置く（2026-11-03）
  - 理由（Claude からの提案）: U6 で更新でも同じ確認が必要なため、登録と更新で同じルールを1か所にまとめる。既存の `GenderValidityDomainService`・`CharacterRelationUniquenessDomainService` と同じ置き方
  - 名前は、既存の「判定する対象 + Validity」にそろえた（Character が重複していた当初の名前をユーザーが指摘し、Claude が提案した `CharacterValidity` をユーザーが了承した。`Valid` ではなく `Validity` にする点も含む）
  - 決定時点では更新の Usecase は未実装で、利用者は登録だけだった（現在は登録・更新の両方が利用する）。Claude はこの案を「U6 を維持する場合の推奨」として提示した
  - 更新時にエンティティの取得で登場人物テーブルと join する案は、確認の代わりにならない。join で確認できるのは変更前の人物で、U6 で確認するのは変更後の人物のため（ユーザーも検討のうえ、ドメインサービスを選択）
- U9: 関係の削除方針は `docs/delete-restore/plan.md` の U9 に従う（2026-11-03 の「物理削除・復元なし」は 2026-11-06 に廃止）
- U10: 人物が論理削除されて一覧に出ない関係（U7）も、ID を指定すれば削除できる状態のままにする。削除 API では人物の削除状態を確認しない（2026-11-03）
  - Claude からの提案の理由: 削除だけであれば影響が小さく、一覧の条件を削除 API に持ち込まなくて済む
- U11: 変更前の人物または相手が論理削除されている関係の更新は、`NOT_FOUND` を返す（2026-11-03）
  - 実装は更新用 Repository の取得で登場人物テーブルと join する。変更後の人物の確認（U6・U8）とは別で、変更後の人物が無効な場合は `INVALID_CHARACTER` のまま
- U12: 人物の削除は論理削除とする（2026-11-03。`docs/delete-restore/plan.md` U4 のとおり）。関係が残っている人物の削除は止める（2026-11-04。未実装）
  - 理由: 確認せずに削除すると、削除済みの人物を指す関係（生きている子データ）が残るため
  - 影響（Claude の整理）: 削除済みの人物に関係が残らない想定になる。U7・U10・U11 は変更していないが、人物の削除時の確認をすり抜けない限り、該当する状況は起きない
- U13: 人物詳細に出す関係は、人物詳細の取得 API（`GET /api/v1/characters/:characterId`）の応答に含め、その人物が関わる関係を両方の向きで返す。専用の API は作らない（2026-11-04）
  - 変わるのは取得だけで、人物の更新（`PUT /api/v1/characters/:characterId`）では関係を扱わない。関係の登録・更新・削除は P5 の API を使う
  - 理由（Claude からの提案）: 人物単位の関係を使うのは人物詳細だけで、1回の取得で済む。書籍詳細が作品を含めて返す `GetBookUsecase` と同じ形で作れる
- U14: 人物詳細でも関係を追加・編集できるようにする（2026-11-04）
- U15: 関係の行の操作は、行末のメニュー（`⋯`）から編集・削除を選ぶ形にする（2026-11-04。ユーザーは「とりあえず」として選択）
  - 理由（Claude からの提案）: 読みやすさと誤操作の防止のため

### 登録 API の実装で Claude が決めた項目（ユーザーの明示的な承認なし）

- P6: 登録のエラー応答（既存の `INVALID_GENDER`・`DUPLICATE_NAME` に合わせた）

  | 状況 | エラー種別 | ステータス | 応答 |
  |---|---|---|---|
  | 人物と相手が同じ | `CHARACTER_RELATION_SELF` | 422 | `targetCharacterId` の項目エラー |
  | 人物・相手が同じ作品の削除されていない人物ではない | `INVALID_CHARACTER` | 422 | 問題のある項目ごとの項目エラー（`characterId`・`targetCharacterId`） |
  | 同じ2人の間に同じ関係名の関係がある | `DUPLICATE_RELATION` | 409 | メッセージのみ |
  | 同じ2人の間に同じ関係名の関係が削除済みのものだけある（U1 の 2026-11-07 の変更） | `DUPLICATE_DELETED_RELATION` | 409 | メッセージのみ |

- P7: U8 のドメインサービスは、true / false ではなく問題のある項目の一覧を返す（`findInvalidFields`）。人物と相手のどちらが問題かを項目エラーで返すため
- P8: 削除済みの人物を指定した場合も、存在しない場合と同じ文言（「指定された登場人物は存在しません。」）を返す

### Claudeの提案（ユーザーは「お願い」とまとめを承認。以下の項目は個別の明示的な承認なし）

- P1: 関係は「A は B の兄」という文の形で表示する。どちらの人物の画面でも同じ文で表示できるので、逆向きの関係名の入力・変換が不要
- P2: 作品詳細の関係タブ（`/works/:workId/relations`）を主な操作場所にする
  - 作品の全関係を文の形で一覧にし、人物で絞り込めるようにする
  - 追加・編集はダイアログで行う（人物・相手の2つを選択し、関係を入力する）。重複などのエラーはダイアログの中に表示する
  - 将来のグラフ表示もこのタブに置く
- P3: 関係の API は人物の登録・更新 API に含めず、独立したリソースにする（人物と関係は守るルールが別。AI 入力で関係だけを承認・登録する流れにも使える）
- P4: 自由入力の表記ゆれ（「兄」「兄貴」「実兄」）による意味上の矛盾・重複は判定しない
- P5: エンドポイント（URL 定数は `api-endpoint.const.ts` の `WORKS_ID_CHARACTER_RELATIONS`・`CHARACTER_RELATIONS_ID` に定義済み。気になるワード・登場人物と同じ形）

  | 操作 | メソッド・URL | リクエストボディ |
  |---|---|---|
  | 一覧 | `GET /api/v1/works/:workId/character-relations` | なし |
  | 登録 | `POST /api/v1/works/:workId/character-relations` | `{ characterId, targetCharacterId, relationName }` |
  | 更新 | `PUT /api/v1/character-relations/:relationId` | `{ characterId, targetCharacterId, relationName }`（U6） |
  | 削除 | `DELETE /api/v1/character-relations/:relationId` | なし |

  - 一覧・登録は作品の関係の集まり（コレクション）の URL、更新・削除は1件の URL にする。関係の ID（ULID）は全体で一意なため、1件は ID だけで識別する（`docs/work-detail/plan.md` P1 の浅いネスト）
  - 登録・更新・削除は、関係タブ・人物詳細のどちらからも同じ API を使う。画面ごとの違いはダイアログの初期値だけ（人物詳細では表示中の人物を `characterId` に選んだ状態で開く）
  - 登録・作品単位の一覧を `/characters/:characterId/relations` にしない理由: 2つの FK は対等で、重複ルール（U1）は向きを問わず2人の組で判定し、表示（U2）も両方の人物に同じように行う。関係は主語の人物の範囲では守れないルールを持つため、登録の範囲は同じ作品であることも確認する作品にそろえる。また関係タブには作品単位の一覧が必要で、人物単位の一覧は両方の向きを集める必要があり主語の人物の下の一覧とは一致しない
  - 人物詳細に出す関係は、人物詳細の取得 API の応答に含める（U13）
    - 経緯: 2026-11-02 に専用の API を作ると決めた。理由の「削除済みの人物の詳細画面は自分の関係を見せる」が U12 で当てはまらなくなり、作品の一覧 API の絞り込み・専用の API・作品の一覧 API への条件追加と比べて、2026-11-04 に U13 へ変更した
    - 人物詳細の取得 API の応答には作品 ID を含め、削除済みの人物も返す（Claude からの提案。U14 の関係の登録に作品 ID が必要で、`docs/delete-restore/plan.md` U4 で削除済みの人物の詳細画面に移るため）
    - 関係タブの人物での絞り込み（P2）は、全件を表示する画面のため、作品の一覧 API を画面で絞り込む形のままとする（Claude からの提案）

```

### 人物詳細の関係セクション（U13〜U15）

```
│ 関係                                     [＋関係を追加]   │
│ ┌──────────────────────────────────────────────────────┐ │
│ │ 山田 は 佐藤 の 兄                               [⋯]  │ │
│ │ 鈴木 は 山田 の 上司                             [⋯]  │ │

- 人物の [編集] と関係の操作は別々に保存する（U13）

## 破綻ケース

- 関係に時間軸（何章から・変化の前後）を持たせる場合: 2人の間の1行では表せず、出来事との結び付け等が必要になる
- 3人以上の集団の関係（「〇〇家」「同じ組織」）を扱う場合: 2人の間の関係というモデルの見直しが必要になる
- 関係をマスタ（区分値）にする場合: U1 の文字列の完全一致による判定を、マスタ ID と逆向きの関係の定義による判定に置き換える必要がある
- 同時に登録された重複がドメインの判定をすり抜けた場合: DB の一意制約違反は 500 になる（登場人物名の重複と同じ扱い）
- 登録と更新で人物の確認の条件が分かれる場合（例: 人物詳細では削除済みの相手との関係も編集できるようにする）: U8 の共通化が合わなくなり、ドメインサービスの分割や条件の追加が必要になる
- 人物詳細で、削除済みの相手との関係も編集できるようにする場合: U11 の `NOT_FOUND` を見直し、取得の条件から人物の削除状態を外す必要がある
- U6 を撤回して人物・相手を変更できなくする場合: 更新で人物の確認が不要になり、U8 のドメインサービスの利用者は登録だけになるため、作成用の Repository への追加で足りる
- 関係を主語の人物の持ち物として扱う方針（人物ごとに重複を判定する、自分が主語の関係だけを表示する等）に変える場合: P5 の URL より `/characters/:characterId/relations` の形が合うようになる
- 関係ごとの履歴（いつ誰との関係だったか）を残す要件が出た場合: U6 の付け替えで過去の人物・相手が上書きされて消えるため、人物・相手の変更を禁止して削除と追加にする等の見直しが必要になる
- 関係タブでも削除済みの人物との関係を見せる場合: U7 の除外条件を外し、人物の削除フラグを一覧で返す必要がある
- 関係を人物と別のタイミングで読み込む場合、ページングが必要な件数になる場合、人物詳細以外でも人物単位の関係が必要になる場合: U13 を見直し、人物単位の関係の取得 API を分ける
- 関係の編集・削除を連続して行う使い方が中心になる場合: U15 のメニューより、ボタンを常に表示する形のほうが速く操作できる
- 関係が残っている人物も削除できるようにする場合: U12 を見直し、削除済みの人物の関係の見せ方（U7・U10・U11・U13）を決め直す必要がある
