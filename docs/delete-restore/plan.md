# 削除・復元の方針

## 概要

書籍・作品・登場人物・登場人物関係・気になるワード・出来事の削除方法と、画面上の復元手段を決める。削除方針はこのファイルにだけ書き、他の設計書からはここを参照する。あわせて、作品の論理削除により書籍更新が通らなくなる既存の問題（後述）の解消方針を決める。

API の URL・画面構成などの詳細設計は未着手。

## 決定事項

### ユーザー決定事項

- U1: 書籍は論理削除とし、ゴミ箱画面から復元できてよい（ゴミ箱の詳細設計は未着手）
- U2: 子データ（作品・登場人物等）専用のゴミ箱画面は設けない（種類ごとに画面が増えてきりがないため）
- U3: 以下の案は採用しない
  - 削除直後の Undo トースト（手間のわりにメリットが小さい。タイミングを逃すと復元できない）
  - 論理削除 + 確認ダイアログのみ（画面上の復元手段なし）
  - 書籍と子データをまとめた1画面のゴミ箱（実装が大変）
- U4: 作品・登場人物は論理削除とし、削除後も一覧のカードを薄く表示して削除済みであることが分かるようにする。カードをクリックして詳細画面に移り、そこから物理削除できるようにする
- U5: 一覧取得 API は削除フラグに関係なく（削除済みも含めて）返す
- U6: 削除済みの作品・登場人物は編集できない
- U7: 削除済みの作品・登場人物の復元は、復元 API からのみ行う（書籍更新・登場人物更新では復元しない）
- U8: （2026-11-07 に U16 により廃止）書籍更新は、フロントエンドで削除済みの作品をリクエストから除外しなくても正しく動くようにする
  - DB 上で削除済みの作品は、リクエストの `deleteFlg` の値に関係なく無視する（タイトル等も更新しない）
  - DB 上で削除されていない作品が、リクエストで `deleteFlg: true` の場合は削除する
  - 例: タブ A で作品 X を削除した後、古い画面のタブ B から X を `deleteFlg: false` で送った場合も無視する。タブ B の他の編集（書籍・他の作品）は保存される
- U9: 利用者が削除できるリソースは、すべて論理削除とし、画面から復元できるようにする（2026-11-06。ユーザーは「とりあえず」として選択）
  - 対象: 書籍・作品・登場人物・登場人物関係・気になるワード・出来事
  - 書籍は U1 のゴミ箱で扱う。それ以外は U4 と同じく一覧に薄く表示し、そこから復元・完全削除（物理削除）できるようにする。U5〜U7 も、登場人物関係・気になるワード・出来事に当てはめる
  - 理由（ユーザー）: 書籍・作品と同じ感覚で関係等を削除したときに、物理削除で消えてしまうのを避けるため。種類ごとに削除方法を決める必要がなくなるため
  - 気になるワード・出来事・登場人物関係を物理削除・復元なしとした以前の決定（2026-10-26〜11-03）は、これにより廃止した
- U10: 書籍・作品を論理削除したら、配下のリソースもすべて論理削除する。復元したら、配下もすべて戻す（2026-11-07）
  - 親の削除前に個別に削除していたものも、親の復元で一緒に戻る。個別に削除していたものを戻さない仕様は設けない
  - 書籍の配下: 作品と、その配下のすべて。作品の配下: 登場人物・登場人物関係・気になるワード・出来事
  - Claude の提案 P1（子に連鎖させない）は、これにより廃止した
- U11: 名前の一意制約は、削除済みも含めて判定する（2026-11-07）
  - 対象: 書籍タイトル・作品名・登場人物名・登場人物関係・気になるワード（現行の一意インデックスの `WHERE delete_flg = 0` を外す）
  - 登録・更新で同じ名前があれば err にする。有効なものと重複した場合（「同じ名前が存在する」）と、削除済みと重複した場合（「復元するか、別の名前で登録する」）で、err の種類を分ける
  - 理由: 削除後に同じ名前で作り直していると、復元（U10 の親の復元を含む）で名前が重複するため
  - 書籍タイトル（2026-11-07）: 一意性のドメインサービスは、違反をドメインが決めるため Result を返す（Claude の提案した案 A をユーザーが選択）。メソッド名は `validate`、err は `DUPLICATE_TITLE`（有効な同名）・`DUPLICATE_DELETED_TITLE`（削除済みの同名だけ）。`DUPLICATE_DELETED_TITLE` は 409「同名の書籍が既に登録されています（削除済み）。復元するか、別のタイトルにしてください。」（Claude の案をユーザーが承認）
  - 登場人物名・登場人物関係・気になるワードも、書籍タイトルと同じ形にそろえる（Claude の提案。登場人物名はユーザーが同じ形で着手し、実装済み）
- U12: 削除済みのカードは、一覧の末尾に表示する（2026-11-07）
- U13: 表示順（作品・出来事）は次のとおり扱う（2026-11-07。Claude が提示した案から、ユーザーが選択）
  - 個別に削除したら、表示順を NULL にする（並びから外す）
  - 親の削除（U10）で連鎖して削除したものは、表示順を変えない
  - 個別に復元したら、削除されていないものの最大値 + 1（末尾）にする
  - 親を復元したら、表示順を持つものはそのまま戻し、NULL のもの（個別に削除していたもの）は ID 順（作成順）で末尾に追加する
  - 理由: 削除済みを末尾に表示する（U12）ため、復元したものも末尾に入る形が表示と一致する。表示順の NULL で「親の削除で消えたもの」と「個別に消したもの」を区別できる
- U14: 親が削除されているのに、子が有効なまま残る状態は作らない（2026-11-07。U10 の前提となる原則）
  - 参照しているだけのもの（作品が参照するアイコンマスタ等）は親子に含めない（Claude の解釈）
  - 著者（`author_transaction`）も書籍の子として、U10 の連鎖の対象にする（原則からの帰結として Claude が提示し、ユーザーが「お願い」と返答）
- U15: タグ（`tag_master`）と書籍とタグの紐づけ（`book_tag_transaction`）は、次のとおり扱う（2026-11-07。U9 の例外）
  - タグの管理画面は設けない。タグは、紐づけが1件もなくなった時点で物理削除する（論理削除済みの紐づけも数に入れる。ゴミ箱の書籍が使うタグを消さないため）
  - 書籍の編集でタグを外したときは、紐づけを物理削除する（復元の手段がなく、タグを付け直せば紐づけも戻るため）
  - 書籍を論理削除したときは、紐づけも論理削除する（U10・U14）。書籍を復元したら戻す。タグはユーザーの子で書籍の子ではないため、変更しない
  - 書籍を完全削除したときは、紐づけを物理削除する（FK が `no action` のため、書籍の行より先に削除する）
  - `tag_master` の `delete_flg` は共通カラムのため残すが、使わない
  - 一意インデックスは2つとも `delete_flg` の条件を外す（タグは物理削除のため。紐づけは削除済みの書籍を編集できない（U6）ため、論理削除済みの紐づけと同じ組み合わせが作られない）
- U16: 作品の削除は書籍更新から外し、作品単位の削除 API で行う（2026-11-07。Claude が提示した案 B をユーザーが選択。削除 API は今後作る）
  - 理由（Claude の提案）: 作品の削除は配下（U10）ごと消える重い操作で、確認と復元を対で持つ独立した操作にするため。書籍の編集の保存に紛れて削除されることを防ぐため
  - 書籍更新のリクエストは削除されていない作品だけを送り、`deleteFlg` を持たない。削除済みの作品の ID が含まれる場合は `WORKS_MISMATCH` にする（Claude が提示し、ユーザーが選択。画面の表示後に削除された作品への変更を黙って捨てないため）
  - これにより U8（削除済みの作品をリクエストから除外しなくても動く・古い画面の他の編集は保存される）と P3・P4 は廃止した。`NEW_WORK_DELETED`・`ALL_DELETED` は書籍更新では起こりえなくなったため削除した。最後の1作品を削除させないルールは、作品の削除 API で守る
- U17: 登場人物関係の復元で、人物または相手が論理削除されている（その作品の削除されていない登場人物ではない）場合は復元せず、409「人物または相手が削除されているため復元できません。先に登場人物を復元してください。」を返す（2026-11-13。Claude が提示した案をユーザーが選択）
  - 理由（Claude の提案）: 復元は入力を受け取らないため、項目ごとの 422 ではなく、リソースの状態による競合として扱う
  - 見送った案: 404（関係の一覧で除外している P2 に合わせる案。復元できない理由が利用者に伝わらない）、422（項目エラーを画面に出す場所がない）

## 解消する既存の問題

現行の書籍更新は、作品を削除済みも含めて全件送ることを求める（`BookAggregate.update`・`matchesExistingWorks`）。一方で、削除済みの作品を返す API がない（書籍詳細の取得は `work_transaction.delete_flg = false` で絞り込み、書籍更新のレスポンスも削除済みを除外）。

このため、作品を1件でも論理削除すると、以降その書籍の更新はすべて `WORKS_MISMATCH`（409）になり、読み込み直しても復帰できない（コードを読んだ結果からの判断で、実際に動かしての確認はしていない）。フロントエンドから書籍更新 API はまだ呼んでいないため、現時点で利用者への影響はない。

U8・P3・P5（書籍集約）と P8 のうち書籍詳細の取得（削除済みの作品を返す）により解消した（2026-10-24）。

## 破綻ケース

- 書籍の編集画面で、作品の削除と復元を一度にまとめて保存したい場合: `deleteFlg: false` を復元として扱う必要があり、古い画面からの更新と区別するための仕組み（バージョン番号等）が別に必要になる
- 削除済みが大量にたまった場合: 一覧が見づらくなるため、「削除済みを表示」の切り替えが必要になる
- 古い画面からの編集が保存されなかったことを、明示的に通知したい要件が出た場合: U8 の「無視する」では伝えられないため、レスポンスへの通知の追加等が必要になる
- 削除したものを元の位置に戻したい要件が出た場合: U13 で個別に削除したものは表示順を消しているため戻せない。削除前の表示順を別の列に持つ必要がある
- 削除した名前を、完全削除せずに使い回したい要件が出た場合: U11 では削除済みも重複の対象になるため、復元・完全削除・別の名前のどれかが必要になる（書籍はゴミ箱で完全削除するまで同じタイトルで登録できない）
- タグの管理画面（名前の変更・一括削除等）を作る場合: タグが利用者の削除するリソースになるため、U15 の物理削除を U9 に合わせて見直す必要がある
- 作品の配下にテーブルを追加した場合: 作品の削除 Repository の連鎖の対象に加えないと、U14 が破れる
- タグにメモ・色等の属性を持たせる場合: 紐づけがなくなった時点の自動削除で属性も消えるため、U15 の自動削除を見直す必要がある
