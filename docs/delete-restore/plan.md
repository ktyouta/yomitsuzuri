# 削除・復元の方針（書籍・作品・登場人物）

## 概要

作品・登場人物の削除を論理削除・物理削除のどちらにするか、画面上の復元手段をどう設けるかを決める。あわせて、作品の論理削除により書籍更新が通らなくなる既存の問題（後述）の解消方針を決める。

API の URL・画面構成などの詳細設計は未着手。

## 決定事項

### ユーザー決定事項

- U1: 書籍は論理削除とし、ゴミ箱画面から復元できてよい（ゴミ箱の詳細設計は未着手）
- U2: 子データ（作品・登場人物等）専用のゴミ箱画面は設けない（種類ごとに画面が増えてきりがないため）
- U3: 以下の案は採用しない
  - 削除直後の Undo トースト（手間のわりにメリットが小さい。タイミングを逃すと復元できない）
  - 論理削除 + 確認ダイアログのみ（画面上の復元手段なし）
  - 書籍と子データをまとめた1画面のゴミ箱（実装が大変）
- U4: 作品・登場人物は論理削除とし、削除後も一覧のカードを薄く表示して削除済みであることが分かるようにする。カードをクリックして詳細画面に移り、そこから物理削除できるようにする
- U5: 一覧取得 API は削除フラグに関係なく（削除済みも含めて）返す
- U6: 削除済みの作品・登場人物は編集できない
- U7: 削除済みの作品・登場人物の復元は、復元 API からのみ行う（書籍更新・登場人物更新では復元しない）
- U8: 書籍更新は、フロントエンドで削除済みの作品をリクエストから除外しなくても正しく動くようにする
  - DB 上で削除済みの作品は、リクエストの `deleteFlg` の値に関係なく無視する（タイトル等も更新しない）
  - DB 上で削除されていない作品が、リクエストで `deleteFlg: true` の場合は削除する
  - 例: タブ A で作品 X を削除した後、古い画面のタブ B から X を `deleteFlg: false` で送った場合も無視する。タブ B の他の編集（書籍・他の作品）は保存される

### Claudeの提案（ユーザーの明示的な承認なし）

- P1: 削除フラグは削除した行にだけ立て、子の行へ連鎖させない。表示・取得時は親の `delete_flg` を JOIN で確認する
  - 子に連鎖させると、復元時に「もともと個別に削除されていた子」と区別できなくなるため
  - 書籍をゴミ箱から復元すると、配下の作品・登場人物もそのまま戻る
- P2: 登場人物を論理削除しても、登場人物関係の行は変更しない（表示上の扱いは未決事項）
- P3: 書籍更新での作品の扱い（U8 を含めた全体）

  | DB 上の状態 | リクエストの内容 | 扱い |
  |---|---|---|
  | 削除されていない | `deleteFlg: false` で含まれる | 通常の更新 |
  | 削除されていない | `deleteFlg: true` で含まれる | 削除する（U8） |
  | 削除されていない | 含まれていない | `WORKS_MISMATCH`（現行どおり） |
  | 削除済み | 含まれていない | 何もしない |
  | 削除済み | 含まれる（`deleteFlg` の値は問わない） | 無視する（U8） |
  | 新規（id が null） | `deleteFlg: false` | 追加する |
  | 新規（id が null） | `deleteFlg: true` | `NEW_WORK_DELETED`（現行どおり） |

- P4: `deleteFlg: true` で削除する作品に、あわせて送られたタイトル・メモ等は反映せず DB の値のままにする（U6 に合わせる）
- P5: 削除済みの作品も集約に読み込んだまま保持し、作品一覧の照合（`matchesExistingWorks`）と不変条件の判定は削除されていない作品だけを対象にする。置き換え後の作品一覧には、削除済みの作品をそのまま付け足す（復元時に別の読み込み方を用意しなくて済むため）
- P6: 書籍更新のレスポンスに、削除済みの作品も `deleteFlg` 付きで含める（古い画面のタブ B でも、レスポンスで描き直せば X が薄いカードになり、削除されたことに気づけるようにするため）
- P7: 書籍更新のリポジトリは、削除済みのまま変わっていない作品を保存の対象から外す（`updated_at` が無用に更新されるのを防ぐため）
- P8: 書籍詳細の取得・作品詳細の取得も、削除済みの作品を `deleteFlg` 付きで返す（U4 の薄いカード・詳細画面に必要なため）
- P9: 削除済みの詳細画面では編集できないようにし、[復元] と [完全に削除] の操作だけを置く
- P10: 作品の復元 API では、削除されていない作品とのタイトル・表示順の重複を集約で判定し、err で返す
- P11: 作品の物理削除では、配下の登場人物・登場人物関係・気になるワード・出来事も削除する（FK が `no action` のため子から順に削除する）
- P12: 登場人物の更新は現行どおり、削除済みを取得から除外して `NOT_FOUND`（404）を返す（`CharacterEntity.update` の throw はそのまま）
  - 書籍更新（U8）で削除済みの作品を無視するのと扱いが分かれるが、登場人物の更新は1件だけを対象にしたリクエストであり、書籍更新は他の作品への編集を守る必要があるため

## 解消する既存の問題

現行の書籍更新は、作品を削除済みも含めて全件送ることを求める（`BookAggregate.update`・`matchesExistingWorks`）。一方で、削除済みの作品を返す API がない（書籍詳細の取得は `work_transaction.delete_flg = false` で絞り込み、書籍更新のレスポンスも削除済みを除外）。

このため、作品を1件でも論理削除すると、以降その書籍の更新はすべて `WORKS_MISMATCH`（409）になり、読み込み直しても復帰できない（コードを読んだ結果からの判断で、実際に動かしての確認はしていない）。フロントエンドから書籍更新 API はまだ呼んでいないため、現時点で利用者への影響はない。

U8・P3・P5 により解消する。

## 未決事項

- 薄いカードの一覧での並び（末尾にまとめるか、元の位置のままか）
- 削除済みの登場人物と同名の登場人物を新規登録できるか（現行の部分一意インデックスでは登録できる。その場合、復元時に名前の重複エラーになる）
- 作品の復元時に表示順が重複した場合のルール（末尾に回す等）
- 登場人物関係・気になるワード・出来事の削除方針（今回の対象は作品・登場人物のみ。詳細画面がない場合の復元・物理削除の操作場所を含む）
- 相関図での、削除済みの登場人物・関係の扱い
- 削除済みの作品に属する登場人物の、一覧・詳細での扱い
- 書籍のゴミ箱の詳細設計
- アイコンマスタのアイコンが論理削除されると、そのアイコンを使う作品を含む書籍の更新が `INVALID_ICON` になる（削除済みの作品に限らない既存の問題。アイコンマスタの削除方針の問題）

## 破綻ケース

- 書籍の編集画面で、作品の削除と復元を一度にまとめて保存したい場合: `deleteFlg: false` を復元として扱う必要があり、古い画面からの更新と区別するための仕組み（バージョン番号等）が別に必要になる
- 削除済みが大量にたまった場合: 一覧が見づらくなるため、「削除済みを表示」の切り替えが必要になる
- 古い画面からの編集が保存されなかったことを、明示的に通知したい要件が出た場合: U8 の「無視する」では伝えられないため、レスポンスへの通知の追加等が必要になる
