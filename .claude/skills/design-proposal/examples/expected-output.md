# Expected Output — 設計案提示

## 入力例

「タスクの削除を論理削除にしたい。どう設計すればいい？」

---

## 期待される出力

```
## 設計案

### 案A: deleted_at カラムを追加する（ソフトデリート）

`tasks` テーブルに `deleted_at TIMESTAMP` カラムを追加し、
削除時に現在時刻をセット、復元時に NULL に戻す。

**メリット**
- 実装がシンプル
- 復元が容易（NULL に戻すだけ）
- 削除日時が記録される

**デメリット**
- 全クエリに `WHERE deleted_at IS NULL` の条件追加が必要
- 条件の書き忘れによるバグリスクがある

**実装コスト**: 低

---

### 案B: is_deleted フラグを追加する

`deleted_at` の代わりに `is_deleted BOOLEAN` を追加する。

**メリット**
- 意味が明示的でわかりやすい

**デメリット**
- 削除日時が記録できない
- 案Aと比べて情報量が少ない

**実装コスト**: 低

---

### 案C: 削除済みテーブルを分離する

`deleted_tasks` テーブルを別途作成し、削除時に移動・復元時に戻す。

**メリット**
- メインテーブルを汚染しない
- 削除済みデータのクエリが分離される

**デメリット**
- 実装が複雑（移動処理・外部キー整合性の管理）
- マイグレーションコストが高い

**実装コスト**: 高

---

## 推奨案: 案A（deleted_at カラム追加）

**理由**: 実装コストが最も低く、削除日時の記録・復元の両方に対応できる。
Drizzle ORM でのフィルタ条件追加も容易。

## 破綻するケース

- 削除済みデータを別のストレージ（アーカイブDB等）に移したい要件が出た場合、案Cへの移行コストが発生する
- 削除件数が膨大になりクエリパフォーマンスが問題になった場合、インデックス設計の見直しが必要になる
```

## 入力例（置き場所の相談）

「全コントローラーで同じ zod のエラーフック（型・構造の違反を固定のメッセージで返す処理）を、どこにまとめるべきか」

---

## 期待しない出力（NG）

```
## 推奨案: presentation/shared/error-message/ を新設する

**理由**: 固定のメッセージはどのコンテキストにも属さないため、共通ディレクトリに置く。
前例として middleware/ の errorHandler・notFoundHandler がある。
```

**NG の理由**:
- 既存の `middleware/` の中身を Read せずに、新しいディレクトリを作る案を出している
- `errorHandler`・`notFoundHandler` は `app.onError`・`app.notFound` で登録するハンドラーで、ミドルウェアではない。実体を確認せずに前例として挙げている
- 新しいディレクトリが既存のどこにも収まらない理由を示していない

---

## 期待する出力（OK）

```
## 設計案

### 案A: middleware/validator/ にミドルウェアとして置く

`zValidator` を固定のフックで包んだ関数を middleware/ に置く。

**根拠**
- `zValidator` は `MiddlewareHandler` を返す（`@hono/zod-validator` の型定義で確認）
- ルート単位で使い、失敗時に固定の応答を返すミドルウェアの前例として `authMiddleware`・`userOperationGuardMiddleware` がある（どちらもコントローラーのチェーンで使われている）

**メリット**
- フック全体（422・message・data の組み立て）を1か所にまとめられる

**デメリット**
- 包むと RPC の型推論が保たれるかを typecheck で確かめる必要がある

**実装コスト**: 低

---

### 案B: presentation/shared/ を新設し、メッセージを返す関数だけを置く

**メリット**
- メッセージの置き場所がプレゼンテーション層にそろう

**デメリット**
- 既存の middleware/ に収まる処理のために前例のないディレクトリを作る
- フックの重複（10か所）は残る

**実装コスト**: 低

---

## 推奨案: 案A（middleware/validator/）

**理由**: 処理の実体がルート単位のミドルウェアであり、既存の middleware/ に収まる。新しいディレクトリは不要。

## 破綻するケース

- 特定の API だけ型・構造の違反に別の応答を返したくなった場合、オプションの追加か素の zValidator への切り戻しが必要になる
```

## 入力例（docs の更新文案）

```
決まった方針を docs に反映する文案を出して
```

## 期待しない出力（NG）

ファイルごとに、追記・置き換えの全文をコードブロックで並べる（数十行になり、ユーザーが読み切れない。方針の本文を複数のファイルに書き写し、ファイル間の食い違いの原因にもなる）。

## 期待する出力（OK）

```markdown
方針の本文は1か所（docs/xxx/plan.md）にだけ書き、他のファイルには参照先だけを書きます。

| ファイル | 変更内容 |
|---|---|
| docs/xxx/plan.md | 決定事項に方針を追加し、廃止した旧決定を1行にまとめる |
| docs/yyy/plan.md | 旧方針の2行を「docs/xxx/plan.md を参照」の1行に置き換える |

要望との対応: 方針の統一 → xxx の決定事項 / ファイル間で食い違わない → yyy は参照のみ

全文が必要であれば出します。この内容で反映してよいですか？
```

## 入力例（質問への回答の途中で設計の選択肢が生じる）

```
著者は書籍の更新時にまとめて更新する
```

（直前の会話: 著者 ID の値オブジェクトに入力値からの生成（fromInput）が必要かを質問された。著者は独自の ID・削除フラグを持ち、書籍の子として一緒に論理削除・復元する方針が設計書にある）

## 期待しない出力（NG）

design-proposal を呼ばずにメイン会話で案を並べ、実装の手間で推奨する。

```markdown
| 案 | ボディの形 | 内容 |
|---|---|---|
| A | `authors: [{ id?, name }]` | ID で特定して更新する |
| B | `authors: string[]` | 名前のリストで全件入れ替える |

B を推奨します。ボディと Usecase が単純になり、ID の存在チェックも不要になるためです。
```

→ 著者は ID とライフサイクル（論理削除・復元）を持つ子エンティティなのに、値として全件入れ替える案を推奨している。推奨理由が修正量・実装の手間で、ドメインモデルとの整合を確認していない。

## 期待する出力（OK）

```markdown
## 設計案

### 案A: 子エンティティとして ID で照合して更新する
- メリット: 著者の ID・作成日時が保たれ、書籍の削除・復元の連鎖と整合する。集約が子を ID で照合する既存の形（作品）と同じ
- デメリット: ボディに ID を含め、集約で既存の著者との照合が必要

### 案B: 名前のリストで全件入れ替える
- メリット: ボディと Usecase が単純
- デメリット: 著者を値として扱うことになり、ID・削除フラグを持つエンティティとしてのモデルと矛盾する。更新のたびに ID が変わる

## 推奨案: 案A
著者はモデル上エンティティ（ID とライフサイクルを持つ）であるため。

## 破綻するケース
- 著者が ID を持たない値（書籍の属性）として扱うようモデルを変える場合は、案B の方が自然になる
```
